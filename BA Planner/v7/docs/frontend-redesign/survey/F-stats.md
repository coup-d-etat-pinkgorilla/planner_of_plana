## 0. 결론 요약

- 시안은 통계 탭을 **3열 고정 레이아웃 + 주제 3개(A 학생 성장 / B 인벤토리 현황 / C 계획 집계)**로 바꾼다. 현재 코드는 `ListView` 안에 `DiagonalSection` 카드를 쌓고, 차트 없이 `Chip`·`ListTile`·`LinearProgressIndicator`·`Text`만 쓴다. **페이지는 사실상 새로 만들어야 한다**(데이터 로딩 `_reload()`와 projection 일부만 재사용).
- `pubspec.yaml` 의존성은 `flutter`, `cupertino_icons`, `file_selector`뿐이다 **[확인]**. 차트 라이브러리는 없다. 코드베이스에 이미 `extends CustomPainter`가 21개 파일에 있다 **[확인]**. 시안 차트는 전부 80° 기울어진 막대·칸, 빗금 패턴, 고정 viewBox×1.25 배율을 쓴다. 그래서 **CustomPainter로 공통 차트 기본 요소(primitive)를 직접 만들 것을 권장한다**(§7).
- 그래프 14종 가운데 **스냅샷 이력이 꼭 있어야 하는 것은 A6·B3 두 개**와 KPI의 "지난 스냅샷 대비" 증감값이다. 현재 `RepositoryState`에는 이력·스캔 시각 필드가 없다 **[확인]**. 따라서 백엔드 프로토콜을 새로 만들어야 한다.
- C3(§6 병목 계단선)와 "페이즈 순" 정렬은 **페이즈가 있는 계획 문서**가 있어야 한다. 현재 통계 페이지는 `RepositoryState.goals`(평면 목표)로 `calculatePlan`/`calculateShortages`만 호출한다 **[확인]**. 그래서 `PlanningDocumentService.calculatePlanningDocument`(phase_results·bottlenecks)를 "활성 계획"과 연결해야 하는데, 서비스에는 "활성 시나리오"라는 개념이 없다 **[확인: scenario_service.dart에 active/selected 없음]**.
- "육성도"(학생별 성장 %)는 A1·A2·A4·A5·C4·C5·KPI의 기반 지표다. 그런데 코드 어디에도 정의되어 있지 않다 **[확인: `육성도` grep 0건]**. 공식을 먼저 확정해야 한다.

### 1.4 쓰지 않는 것 · 데이터 규칙 (원문)
- ✕ 원·도넛: 구성비는 100% 누적 막대로 그린다.
- ✕ 이중 축: 단위가 다르면 작은 배수(small multiples)로 나눈다.
- ✕ 다른 재화 합산: 크레딧과 노트를 더하지 않고 충족률(%)로 비교한다.
- ✓ 모름 ≠ 0: 스캔이 없으면 빗금과 '스캔 없음', 0은 빈 막대로 그린다.
- ✓ 색은 역할별로 하나: 크기 = 파랑 한 색조, 강조 = 분홍 + 회색.
- ✓ 상태색은 상태 전용: 초록·노랑·빨강은 늘 아이콘이나 글자와 함께 쓴다.
- ✓ 범례 + 직접 라벨: 2계열 이상이면 범례를 두고 선 끝에 이름을 붙인다.
- 범례: 크기(파랑 `#71c7f4`) · 강조·부족(분홍 `#f2b3ef`) · 나머지(회색) · 과잉(노랑) · 모름(빗금)

### 1.6 확정 사항 (원문 그대로)
1. **범위: 기본 프로필 전체 + 머리글 토글** — 토글로 학생 탭 필터 기준을 고를 수 있습니다. 필터 기준이면 제목 옆에 칩으로 표시하고, **A1~A6만 바뀌며 B·C는 그대로 둡니다.**
2. **1차 KPI·차트 목록 고정** — **K · D · A1 · A2 · B1 · C1 · C2를 1차로 고정합니다. 2·3차는 스냅샷이 쌓인 뒤 붙입니다.**
3. **병목 시각화: C3 계단선** — §6 기준(단계 순서대로 보유량 차감)으로 첫 부족 단계와 이후 누적 부족을 계단선으로 그립니다.
4. **스냅샷 1회일 때 추이 자리** — A6·B3는 스냅샷이 2회 이상일 때만 그리고, 1회면 그래프 자리에 다음 문구를 둡니다: **"스캔을 더 실행하면 변화가 나타납니다."**

## 6. 사용자 확인이 필요한 모호점

1. **범위 모델 충돌 (중요)**: Proposal 확정 사항 1은 "머리글 **토글**로 **학생 탭 필터** 기준"이다. 반면 Stats-Growth·Filter-Open artboard는 **통계 전용 필터**("학생 탭 필터와 따로 저장", 팝업에 `학생 탭 필터 불러오기`)를 쓰고 머리글 토글이 없다. "A1~A6만 바뀌고 B·C는 그대로"라는 점은 두 쪽이 같다. → 최신 artboard(통계 전용 필터 + 불러오기)를 정답으로 볼지 확인이 필요하다.
2. **KPI 구성 충돌**: Proposal K는 주제를 가로지르는 한 줄(보유 학생·평균 육성도·완전 육성·계획 충족률·부족 재화·엘레프, 최대 6개)이고 "누르면 해당 그래프로 스크롤(부족 재화 → C1)"이다. artboard는 **주제마다 따로** KPI 5개를 두고 서로 다른 지표(최대 레벨·계획 등록·과잉 재화·첫 부족 등)를 쓴다. 주제를 넘나드는 스크롤(성장 화면에서 C1으로)은 artboard 구조에서는 불가능하다.
3. **"2·3차는 스냅샷이 쌓인 뒤"**: 실제로 이력이 필요한 것은 A6·B3뿐이다. A3·A4·A5·B2·C3·C4·C5는 이력 없이 계산된다. 차수가 "구현 순서"인지 "데이터 조건"인지 확인이 필요하다. 그리고 artboard에는 2·3차 위젯이 1차와 함께 항상 보인다(차수 칩만 붙어 있음). 1차 출시 때 2·3차 자리를 숨길지, 빈 카드로 둘지도 정해야 한다.
4. **육성도 공식 미정**: 학생별 육성도(%)의 정의(어떤 필드를, 어떤 가중치로, 최대값 기준(`planElementTargetMaximums`)인지, 성급별 상한 반영인지, 미보유는 제외인지), "완전 육성", "최대 레벨"(레벨 90?), "스킬 낮음/레벨 낮음/장비 뒤처짐" 판정 기준이 모두 정해져야 한다.
5. **A2 항목 vs 오른쪽 요약**: 요약의 "가장 낮은 항목 **애장품** 31%"는 A2 항목 목록(레벨·EX·일반 스킬·장비·성작·전용무기)에 없다. 항목 목록에 애장품·인연·추가 능력치를 넣을지 정해야 한다. A2의 "일반 스킬"이 skill1~3 전체인지, A5 행의 "일반/강화/서브"와 어떻게 대응하는지도 불명확하다.
6. **A5 "장비" 행 열 구간**: 열이 스킬 레벨(1–3/4–6/7–8/9/M)인데 장비 행이 같은 열을 쓴다. 장비 티어(T0~T10)나 레벨(0~70)과의 대응이 불명확하다.
7. **D 이동 목적지 존재 여부**: "학생 탭 · 필터: 육성도 60~70%"인데, 학생 필터 팝업(Student-Filter, Stats-Filter-Open)에는 **육성도 범위 행이 없다**. "인벤토리 · 티어별 충족률", "인벤토리 · 부족 위험 · 해당 행 선택 · 획득처", "인벤토리 · 분석 · 최근 변화", "계획 만들기 2·3"의 deep link 대상 UI가 다른 그룹 시안에 실제로 있는지 교차 확인해야 한다. "← 통계" 칩은 Proposal에만 있고 다른 탭 artboard에는 없다 **[확인: grep 결과 Statistics-Proposal 1건]**.
8. **필터 항목 vs 코드 모델**: 팝업의 "장비 티어/레벨 = 3칸 중 가장 낮은 칸", "추가 능력치 = HP·ATK·HEAL **합** 0~25", "성급 = 학생★ + 전용무기★ 결합"은 현재 `StudentRangeConditions`(필드별 lower/upper: equip1_tier…, stat_hp…)와 모양이 다르다. 합의 상한 25도 필드별 최대 25×3과 맞지 않는다. 이 부분은 학생 탭 그룹과 같이 결정해야 한다.
9. **"활성 계획"의 정체**: "활성 계획 · 9명 · 페이즈 5"가 현재 편집 중인 계획 문서인지, 저장된 시나리오 중 선택된 것인지, `RepositoryState.goals`인지 정해야 한다.
10. **시안 수치 불일치**: 기술 노트(최상급)가 C1에서는 96/120, Inventory 상세에서는 필요 254·부족 158, C2 상세에서는 충족률 24%다. A5는 필터 전후 수치가 같다. 모두 예시 값으로 보이며 구현 판단에는 영향이 없다 **[추정]**.
11. **빈 상태 카드 높이**: Growth-Filter의 빈 A4·A6 카드가 368→328로 줄어든다. "그래프마다 원래 비율 유지" 원칙과 빈 상태 예외를 어떻게 다룰지 정해야 한다.
12. **B3 세그 `스냅샷 6회 / 4주 / 전체`**: "스냅샷 6회"와 "전체"가 어떻게 다른지 불명확하다.

## 7. 차트 구현 방식 판단: CustomPainter vs 라이브러리

**확인한 사실**
- `pubspec.yaml` dependencies: `flutter`, `cupertino_icons ^1.0.8`, `file_selector ^1.1.0`. 차트 패키지 없음.
- 코드베이스에 `extends CustomPainter`가 21개 파일에 있다(사선 섹션, 스크롤바, 필터 그룹 카드, 별 세그먼트 `studentStarSegmentPath` 등). 80° 기하 helper(`buildRoundedSectionPolygon`, `studentStarSegmentDepth`의 `tan(80°)`)도 이미 있다.
- 시안 차트의 특징: ① 막대·칸·트랙에 `skewX(-10)`(80°) 적용 ② 빗금 `pattern`(rotate 45, "모름"·"부족분"·"해당 없음") ③ 고정 viewBox에서 그린 뒤 **균일 1.25배**(선·글자 함께) ④ 직접 라벨(선 끝 이름), 분홍 강조 구간, 4분면 평균선 ⑤ 차트 요소마다 탭·hover(점 팝오버, 막대·칸 선택 → 오른쪽 근거 갱신).

**판단: CustomPainter로 직접 그리기를 권장한다 [추정·근거 있음]**
1. 80° 기울어진 막대·히트맵 칸·트랙과 빗금 채우기는 fl_chart 같은 일반 라이브러리의 기본 마크로 표현되지 않는다. 결국 커스텀 painter hook이 필요해지므로 라이브러리의 이점이 줄어든다.
2. "viewBox 설계 좌표 × 1.25 균일 배율"은 `CustomPainter`에서 `canvas.scale(1.25)` 한 번이나 `FittedBox`+`AspectRatio(viewBox 비율)`로 그대로 옮길 수 있다. 그래서 시안 좌표를 1:1로 이식하고 픽셀 비교하기가 쉽다. 라이브러리는 자체 레이아웃·패딩·폰트 스케일 규칙이 있어 시안 좌표와 맞추기 어렵다.
3. 그래프 종류는 14개지만 마크 종류는 많지 않다: 막대(세로/가로/발산/누적), 점(산점/스트립/덤벨), 선(꺾은선/계단/점선 기준), 칸(히트맵). 축 범위·데이터 양도 작다(최대 수백 점, 학생 ≤ 약 200). 성능이나 상호작용 측면에서 라이브러리가 꼭 필요하지 않다.
4. 기존 코드 관례(geometry 함수를 public으로 두고 widget test에서 rect·path를 검증하는 방식, 예: `studentStarSegmentRects`)를 따를 수 있다. 의존성을 추가하면 README의 런처가 pubspec 지문 변경으로 Release를 다시 빌드한다 **[확인: README 104~106행]**. 큰 문제는 아니지만 고려할 점이다.
5. 히트 테스트: painter가 쓰는 geometry 객체(막대 rect, 점 중심, 칸 path)를 별도 클래스로 계산해 `GestureDetector`/`MouseRegion` 레이어에서 공유하면 된다(점 hover 팝오버, 막대 선택).

**제안할 공통 primitive [추정]**: `StatChartFrame`(viewBox 크기 + 1.25 배율 + AspectRatio), `SkewedBar`(80° 둥근 막대 path), `HatchPaint`(45° 빗금 shader/패턴), `StatAxis`(눈금·기준선·평균선), `DirectLabel`, `StatChartPalette`(크기 파랑 `#71c7f4` α.72, 강조 분홍 `#f2b3ef`, 회색, 과잉 노랑, 상태 초록 `#7fe3bd`), `StatChartGeometry`(hit-test 공유). 이 위에 그래프별 painter 14개를 얹는다.
