# 알파 배포 방식 결정안 (2026-10-19, CM 초안 — 사용자 확정 대기)

이미 확정된 전제(2026-09-27): 게임 이미지는 배포본에 싣지 않고 첫 실행 때 사용자 설치본에서 키 불필요 파일만 추출한다. 키가 필요한 표에서 나온 자료는 배포자가 패치마다 갱신하는 스냅샷으로 동봉한다. Windows Release에 Python venv를 `release/backend/`로 포함한다. 개발자 도구는 배포본에 없다.

남은 결정 3개. 각각 CM 권고안과 대안, 고르면 생기는 후속 작업을 적는다.

## 결정 A — 설치 형태
- **권고: zip 압축본 1개** (`BA-Planner-v7-alpha-<날짜>.zip` → 풀고 `BA Planner v7.exe` 실행). 설치·레지스트리·관리자 권한 없음. 사용자 데이터(계정·스캔 결과·인식 샘플)는 exe 옆이 아니라 `%LOCALAPPDATA%\BA Planner\v7\`에 두어 zip을 새 버전으로 바꿔도 남게 한다.
- 대안: 인스톨러(Inno Setup 등). 업데이트·제거·바로가기까지 같이 풀어야 해서 알파 범위를 두 배로 키운다. 정식 때 재검토.
- 후속: 데이터 경로가 지금 exe 상대 경로인지 확인(XB), 아니면 1 slice. README 첫 줄에 "압축 풀고 실행" 3줄.

## 결정 B — 업데이트: **"깃허브에서 한 번만 받고, 그 뒤는 알아서 갱신"** (사용자 규칙 2026-10-19 22:09, 확정)
- 사용자 규칙이 이것 하나다. 나머지 방식은 CM 재량. 따라서 B는 "알림만"이 아니라 **자동 업데이트**로 바꾼다.
- 구조(런처 패턴, 권고): zip 안에 **런처 exe + `app/` 폴더**. 사용자는 런처만 실행한다. 런처가 (1) GitHub Releases의 `latest.json`을 읽고 (2) 새 버전이면 zip을 `app-staging/`에 내려받아 **SHA-256 검증** 후 (3) `app/` ↔ `app-staging/` 폴더 교체, 실패하면 이전 `app/`로 복귀(롤백) (4) 앱 실행. 교체는 앱이 안 떠 있는 런처 단계에서 하므로 Windows 파일 잠금 문제가 없다. 지금 최상위 `BA Planner v7.exe`가 이미 "지문 비교 → 재빌드 → 실행" 런처라 같은 자리에 "지문 비교 → 다운로드/교체 → 실행"으로 바꾸면 된다(개발 모드/배포 모드 분기).
- 오프라인·GitHub 장애: 조회 실패 시 조용히 현재 버전 실행(업데이트는 다음 시작 때). 다운로드 중 끊기면 staging만 버린다.
- **데이터 스냅샷도 같은 채널**: `latest.json`에 `appVersion`과 `dataVersionId`(lock version-id)를 따로 두고, 앱은 그대로이고 자료만 바뀐 "데이터 전용 릴리스"(작은 zip: `backend/data/*` + 스냅샷 메타)를 허용한다. 게임 패치 뒤 M5→M6으로 자료만 다시 올리면 사용자 쪽은 다음 시작 때 자동 반영.
- 사용자 선택: 설정에 "자동 업데이트 끄기"와 "지금 확인" 둘만. 베타/정식 채널 구분은 알파 밖.
- 알려진 한계(알파에서 감수): 코드 서명이 없어 첫 다운로드 때 SmartScreen 경고가 뜬다(README에 한 줄). 런처 자신의 갱신은 "다음 버전 zip을 받아 런처만 수동 교체" 안내로 남긴다(런처는 거의 안 바뀌게 작게).
- 후속(알파 차단): `latest.json` 형식 1개(appVersion, dataVersionId, zipUrl, sha256, notes, minLauncher), 런처 수정(XB 또는 CF — 런처가 Dart인지 PowerShell 래퍼인지에 따라 소유 결정), M6이 릴리스마다 `latest.json`·zip·sha를 생성, GitHub Releases 업로드는 사용자.

## 결정 C — 알파 테스터
- **권고: 공개 전에 1~2명에게 zip 전달**, "본인 PC 아닌 곳에서 첫 실행 → 첫 스캔 → 첫 계획"까지 가는지만 본다. 테스터에게는 스캔 진단 JSON(이미 있음)과 막힌 지점 메모만 받는다.
- 이 한 번이 UI 최종 검토 목록과 튜토리얼 항목을 추측이 아닌 관측으로 바꾼다. 테스터가 없으면 본인이 **깨끗한 Windows 계정**(새 사용자 계정)에서 같은 절차를 밟는 것으로 대체.
- 후속: 테스터용 1장 안내(설치 경로 요구사항: Steam 블루아카 설치, 창 모드 1280×720 이상, DPI 100 %).

## 결정 D — 실기 수용 검증 (사용자 추가 2026-10-19 22:14, 확정)
배포 zip을 만들기 직전, 차단 항목 구현 뒤에 **실제 KR 클라이언트로 한 번 끝까지** 돌린다. 개발 중 측정(O2 1080/1440, 720 장비 104/104)은 기준팩 교체(`1ee862ae`)·source30·FB-10 연결 이후 유효하지 않다.
- 대상: 사용자 PC, 창 1280×720 / 창 1920×1080 / 전체화면 2560×1440.
- 항목: 학생 단일 5명(등급·장비 섞어서), 학생 전체 1회, 인벤토리 그리드 탭별 1회, (긴 이미지 방식이 채택돼 있으면) 엘레프 1회.
- 통과 기준: 첫 1회 측정으로 숫자를 정한다 — 학생 스탯 4값 일치율, 인벤토리 수량 오답 0·미확정 ≤ N, 전체 스캔 소요 ≤ T. 미달이면 그 항목만 고치고 재측정.
- 증거: 앱의 스캔 진단 JSON(`ba-planner-student-scan-*.json`, 계정명·스크린샷 미포함)만. 스크린샷 반복 비교 없음.
- 분류: 틀린 건 XB가 진단 JSON으로 계산식 / 메타데이터 / 인식기 중 어느 경계인지 나눈다.
- 두 번째 PC(테스터 또는 새 Windows 계정)에서 같은 항목 1회 — 여기서 **첫 실행 추출(합성 템플릿이 그 PC에서도 생성)** 이 같이 검증된다. 결정 C와 합친다.
- 소유: 절차·진단 수집 스크립트 XB, 실행 사용자, 판정 CM.

## 결정 E — 스캔 문제 신고 기능 (사용자 추가 2026-10-19 22:18, 확정)
폴백·미감지·미확정이 생긴 스캔을 사용자가 한 번에 신고할 수 있어야 알파 뒤 최적화가 추측이 아니라 데이터가 된다.
- **자동 감지**: 스캔 세션이 끝났을 때 (a) 폴백 경로를 탄 셀 수 (b) 미확정 수 (c) 인식 실패로 비운 슬롯 수를 센다(이미 evidence/status 이벤트에 있는 값의 집계). 한계(첫 측정으로 정함)를 넘으면 검토 화면 위에 막지 않는 띠 한 줄: "이번 스캔에서 N개를 못 읽었어요 — 신고하면 다음 버전 개선에 씁니다". 수동으로도 검토 화면·설정에 "스캔 문제 신고" 버튼.
- **신고 묶음(zip, 로컬 저장)**: 진단 JSON + 폴백/미확정 **셀 조각 이미지만**(전체 스크린샷 아님, 체크박스로 끌 수 있음) + 앱 버전·데이터 version-id·창 크기·DPI·스캔 프로파일 + 사용자가 적는 한 줄. 계정명·게임 창 제목·다른 학생 정보 제외(기존 진단 JSON 원칙 그대로).
- **보내기**: 자동 업로드 없음. zip을 만들고 폴더를 연 뒤, GitHub Issues 새 글 링크(제목·버전 미리 채움)를 띄운다. 사용자가 첨부해 올린다. 알파에서는 이걸로 충분하고, 자동 업로드는 서버·동의 문제라 밖.
- **개발 쪽 수용**: XB가 신고 zip을 그대로 replay fixture로 넣을 수 있는 형식(기존 골든 시나리오와 같은 모양)이어야 한다. 즉 신고 = 회귀 테스트 재료.
- 소유: 집계·zip 묶기·fixture 호환 = XB(FB 요청서), 띠·버튼·체크박스 = CF.

## 알파 완료 정의 (다섯 과제의 공통 기준)
**본인이 옆에 없어도 다른 사람이 zip을 풀어 첫 스캔과 첫 계획까지 가는 것.** 이 문장에 필요 없는 일은 알파 뒤로 미룬다.

## 알파 차단 항목 (이 결정안 기준)
1. 첫 실행 추출 구현(CF) — 없으면 아이콘이 빈 상자.
2. M6 스냅샷 메타·`latest.json`·zip sha 생성(XB) — 작은 스크립트 2개.
2-1. **자동 갱신 런처**(다운로드·검증·폴더 교체·롤백·실행) — 사용자 규칙의 핵심.
2-2. **실기 수용 검증(결정 D)** — zip 직전 1회 + 두 번째 PC 1회.
2-3. **스캔 문제 신고(결정 E)** — 집계·zip·띠·버튼.
3. 사용자 데이터 경로 확인(XB) — zip 교체 안전.
4. 첫 실행 체크리스트(튜토리얼 구상 문서 참조, CF).
그 외(M3 SchaleDB 제거, M4, 스캔 긴 이미지 채택, O3 승격, A2)는 알파 뒤로 미뤄도 사용자 경험이 바뀌지 않는다.
